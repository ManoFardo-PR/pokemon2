# Database Portability Rules & SQL Guidelines

## 1. Why Portability Matters
Per Architectural Decision **D-002**, PokeSearch 2 runs locally on an embedded SQLite database using Node 24's native `node:sqlite` driver. To ensure future hosted deployments can transition to Postgres without requiring a complete database rewrite (scheduled in **S08.T03**), all schemas, queries, and transactions adhere to strict cross-engine portability guidelines.

---

## 2. Portable Core Principles
- **Explicit Primary Keys**: Use natural, persistent string identifiers provided by authoritative sources (e.g., set IDs, card IDs) or client-generated UUIDs.
- **ISO-8601 UTC Timestamps**: Store all date-time values as ISO-8601 formatted text strings (`YYYY-MM-DDTHH:MM:SS.sssZ`).
- **Standard Types Only**: Limit column definitions to portable types: `TEXT`, `INTEGER`, and `REAL`.
- **Explicit Column Lists**: Always specify target columns in `SELECT` and `INSERT` statements (`SELECT a, b FROM ...` instead of `SELECT *`).
- **Parameterized Queries**: Never interpolate or concatenate values into SQL strings. Use prepared statement parameter binding (`?` or `$param`).
- **Standard Upserts**: Write upsert operations using SQL-standard `ON CONFLICT (...) DO UPDATE SET ...` or `ON CONFLICT (...) DO NOTHING`.
- **Explicit Named Indexes**: Always name indexes deterministically using standard prefixes (e.g., `idx_<table>_<column>`).

---

## 3. Forbidden SQL Constructs
- `INSERT OR REPLACE`: Deletes and re-inserts rows, firing cascade deletes unexpectedly. Use `ON CONFLICT (...) DO UPDATE`.
- Implicit `rowid`: Do not depend on SQLite's internal rowids or table auto-rowid keys in business logic.
- Engine-specific autoincrement quirks (`AUTOINCREMENT` behavior beyond monotonic identity).
- Double-quoted string literals: Double quotes (`"`) are reserved strictly for identifiers; single quotes (`'`) are for string literals.
- `LIMIT` clauses on `UPDATE` or `DELETE` statements (unsupported in standard Postgres).
- Direct equality comparison on JSON columns (`WHERE col_json = '...'`). Use dialect helper extraction.

---

## 4. Column & Table Naming Conventions
- Table and column names: `snake_case`.
- Columns storing JSON payloads: Suffix with `_json` (e.g., `raw_json`, `metadata_json`).
- Timestamp columns: Suffix with `_at` (e.g., `created_at`, `updated_at`, `deleted_at`).
- Normalized text search helpers: Suffix with `_norm` (e.g., `name_norm`).
- Junction / relationship tables: `<parent>_<child>` (e.g., `deck_cards`, `set_legalities`).

---

## 5. Dialect Module (`packages/db/src/dialect`)
When queries require engine-specific SQL constructs, callers must never write inline engine-specific SQL. Instead, consume expressions generated by the `Dialect` interface:
```ts
export interface Dialect {
  readonly name: "sqlite" | "postgres";
  jsonArrayElements(expr: string, alias: string): string;
  jsonContains(column: string, param: string): string;
  fullTextMatch(table: string, query: string): string;
  rank(weights?: Record<string, number>): string;
  upsert(table: string, columns: readonly string[], conflictTarget: readonly string[]): string;
  nowUtc(): string;
  numericOrder(column: string): string;
}
```

---

## 6. Migration Tagging Rules
Any migration script that utilizes SQLite-specific constructs must explicitly wrap the block with migration tags:
```sql
-- @postgres: jsonb_array_elements(raw_json->'cards')
-- @sqlite-only
SELECT value FROM json_each(raw_json, '$.cards');
-- @end
```
Enforced by `scripts/sql-lint.mjs` during `pnpm check`.

## 7. Known Engine Divergences Table

| SQLite Construct | Postgres Target Equivalent | Rationale & Porting Strategy |
|---|---|---|
| `*_json TEXT` | `jsonb` + GIN Index | SQLite stores JSON as TEXT; Postgres optimizes with binary `jsonb`. |
| `cards_fts` (FTS5) | Generated `tsvector` + GIN Index | Weighted full-text search: SQLite uses `MATCH` + `bm25`; Postgres uses `to_tsvector` + `@@`. |
| `cards_market_usd` | Materialized View (`cards_market_usd`) | SQLite computes aggregates or table views; Postgres manages materialized refresh. |
| `json_each(...)` | `jsonb_array_elements(...)` | Array unwinding in relational joins. |
| `CAST(number AS INTEGER)` | `NULLIF(regexp_replace(number, '\D', '', 'g'), '')::int` | Handling non-numeric suffixes in card numbering (e.g., "12a"). |
| `VACUUM INTO '<file>'` | `pg_dump -Fc` | Consistent offline atomic database snapshots. |
| `strftime('%Y-%m-%dT%H:%M:%fZ', 'now')` | `now() at time zone 'utc'` | UTC timestamp generation. |

---

## 8. Transaction & Locking Model
- **SQLite**: Write transactions execute via `BEGIN IMMEDIATE` to acquire reserved locks upfront, preventing deadlocks. Readers run concurrently under WAL mode without blocking writers.
- **Durability**: Configured with `PRAGMA synchronous = NORMAL`, balancing durability against I/O throughput for single-user workloads.
- **Postgres Translation**: On Postgres, `BEGIN IMMEDIATE` maps directly to standard `BEGIN`, and SQLite's `busy_timeout` maps to `SET lock_timeout`. `SAVEPOINT` nesting semantics remain identical across both engines.

## 9. Type Mapping Matrix

| Logical Type | SQLite Affinity | Postgres Data Type | TypeScript Mapping |
|---|---|---|---|
| Identifier / UUID | `TEXT` | `TEXT` or `UUID` | `string` |
| Short String | `TEXT` | `VARCHAR(N)` or `TEXT` | `string` |
| Long Text / Description | `TEXT` | `TEXT` | `string` |
| Small / Big Integer | `INTEGER` | `INTEGER` or `BIGINT` | `number` / `bigint` |
| Floating Point / Price | `REAL` | `NUMERIC(10,2)` or `DOUBLE PRECISION` | `number` |
| Boolean Flag | `INTEGER` (0 / 1) | `BOOLEAN` | `number` / `boolean` |
| ISO Timestamp | `TEXT` | `TIMESTAMPTZ` | `string` |
| JSON Payload | `TEXT` | `JSONB` | `string` / `Record<string, unknown>` |
| Binary Blob | `BLOB` | `BYTEA` | `Uint8Array` |

## 10. Six-Item Review Checklist for New Migrations
1. [ ] Are all primary keys explicitly typed and non-empty?
2. [ ] Are timestamps formatted as UTC text ending with `Z`?
3. [ ] Are all JSON columns named with `_json` suffix?
4. [ ] Are all SQLite-specific features wrapped in `-- @sqlite-only` / `-- @end` with a matching `-- @postgres:` note?
5. [ ] Is the migration free from `INSERT OR REPLACE` and double-quoted string literals?
6. [ ] Does `pnpm check` (including `sql-lint.mjs`) pass cleanly?
